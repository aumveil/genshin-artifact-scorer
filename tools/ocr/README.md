# OCR 截图识别

游戏里打开圣遗物详情页，按 `Alt+S`，网页直接跳到「价值评估」并给出结论——省去手打 4 条词条。

> **可选附属工具。** 需要 Python 环境与本目录下的依赖；
> 网页主体（`js/` + `index.html`）仍然是纯前端、零安装、`file://` 直开。
> **服务没启动时网页与以前完全一样**，桥接探测不到就静默禁用，不报错、不提示。

---

## 1. 怎么用

```
1. 双击 run.bat            → 启动服务（控制台窗口，Alt+S 识别 / Alt+Q 退出）
2. 浏览器打开 index.html    → 与平时一样
3. 游戏里打开圣遗物详情页
4. 按 Alt+S                → 网页自动切到「价值评估」，直接出结果
```

**不需要**先进某个角色的详情页，也不需要停在任何特定页面。

识别不完整时（缺部位、缺套装、词条片段无法解析）会**回退到录入弹窗**，把识别原文摆出来让你改。

### 依赖

```bash
pip install rapidocr-onnxruntime --proxy http://127.0.0.1:7890
```

本机已装在项目专用环境 `%USERPROFILE%\.workbuddy\binaries\python\envs\default`，
`run.bat` 会自动使用它。**直接用系统 `python ocr_service.py` 会报 ModuleNotFoundError**——
OCR 依赖不在系统 Python 里。

## 2. 架构

```
┌──────────────────────────┐         ┌────────────────────────────────┐
│  Python 常驻进程          │         │  网页（file:// 打开）           │
│                          │         │                                │
│  热键监听（Alt+S/Q）      │         │  js/ocr-bridge.js              │
│  抓图 → 裁剪 → OCR        │         │    ↓ fetch 轮询 /latest         │
│  过滤 + 完整性检查         │◄────────┤  App.ui.receiveOcrArtifact()   │
│  HTTP :18080             │  HTTP   │    ↓                           │
│    GET /api/ocr/health   │         │  解析 → pendingArtifact        │
│    GET /api/ocr/latest   │         │    ↓                           │
│    POST /api/ocr/ack     │         │  渲染「价值评估」→ 出结论        │
└──────────────────────────┘         └────────────────────────────────┘
```

**两个关键原则**

1. 服务是可选增强，缺了网页必须完全正常。
2. **OCR 不新增任何 UI**：网页侧只加一个 `receiveOcrArtifact()` 入口，其余全部复用现有的评估页。

### 网页侧改动（共 4 处）

| 文件 | 改动 |
|---|---|
| `js/ocr-bridge.js` | **新增**。轮询服务 → 取件 → 交给 UI；无 `fetch` 环境/无服务时静默禁用 |
| `js/ui.js` | 新增 `receiveOcrArtifact(payload)` 并导出 |
| `index.html` | 末尾引入 `ocr-bridge.js` |

**回退**：删掉这三处即完全恢复原状，现有功能不依赖其中任何一处。

`receiveOcrArtifact` 必须写在 `ui.js` 内部——它要用模块私有的
`pendingArtifact` / `evalHidden` / `view` / `startAssessFlow`。

### 为什么解析放在前端

服务端只输出「过滤后的文本 + 可疑项」，由网页的 `parser` 解析。
词条别名表 / 套装表 / 档位表都在 `js/constants.js`，Python 抄一份必然与网页不同步，
而且**不同步时不会报错**，只会悄悄给出错分。

## 3. 协议

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/ocr/health` | 探测，返回 `{ok, service:"gys-ocr", version}` |
| GET | `/api/ocr/latest?since=N` | 有新件 200 + JSON，无则 **204** |
| POST | `/api/ocr/ack` | 确认已消费，服务端清空（防刷新重复弹窗） |

端口按 `18080 → 18081 → 18082` 依次尝试。**前后端用同一份候选列表，无需共享配置**。

CORS 必须回 `Access-Control-Allow-Origin: *`（`file://` 页面的 origin 是 `null`）
+ `Access-Control-Allow-Private-Network: true`（Chrome 的 PNA 预检要求）。

**服务端不开放外部写入端点**，外部页面最多能读，不能写。

响应体：

```json
{
  "seq": 17, "ts": 1762700000000, "ok": true,
  "text": "绯花之壶\n空之杯\n物理伤害加成\n58.3%\n+20\n防御力+21\n…\n绝缘之旗印：（0）",
  "lines": ["绯花之壶", "空之杯", "…"],
  "suspicious": [{ "field": "防御力+", "reason": "缺少数值，可能被光效遮挡或识别失败" }],
  "elapsed_ms": 1221
}
```

失败时 `ok:false` + `error` + `message`。错误码：
`NO_WINDOW` / `BLANK_FRAME` / `OCR_EMPTY` / `OCR_INCOMPLETE` / `ENGINE_ERROR`。

## 4. 关键实现约束（改代码前必读）

### 4.1 抓图：只能用 BitBlt，且必须声明 DPI 感知

| 约束 | 原因 | 违反后果 |
|---|---|---|
| `SetProcessDpiAwareness(2)` 必须在任何尺寸查询之前 | 125% 缩放下 `GetClientRect` 返回逻辑像素 | 只抓到画面左上 **80%** |
| 只用 `BitBlt`（窗口 DC） | `PrintWindow` 的 flag 0 与 flag 2 对本游戏均返回 0、纯黑 | 拿到全黑图 |
| 必须检测黑图 | 窗口最小化时 BitBlt 可能返回黑 | 静默产出垃圾数据 |

**不需要激活游戏窗口**（实测前台为其他程序时照样能抓，BitBlt 读窗口 DC 与焦点无关）。
但**不能被其他窗口遮挡**（会抓到遮挡物）、**不能最小化**（黑图）。

### 4.2 裁剪比例

```python
"crop_ratio": [0.725, 0.055, 1.0, 0.52]
```

依据 2130×1191 窗口标定。**下界 0.52 是实测扫描出来的**：

| 下界 | 面板高 | OCR 行数 | 耗时 | 套装名 |
|---|---|---|---|---|
| 0.56 | 601 | 14 | 1794ms | ✅ |
| **0.52** | **554** | **12** | **1175ms** | ✅ |
| 0.50 | 530 | 12 | 1126ms | ✅ |
| 0.49 | 518 | 11 | 1004ms | ❌ 整行丢失 |

套装名位于详情栏底部（面板内约 **92%** 高度处），余量很薄。
更宽松的值会白识别「2 件套/4 件套」的描述文字——那些对下游毫无用处。

> ⚠ **窗口尺寸变化未验证**。4K（3840×2160）下曾抓到的是队伍界面（当时不在圣遗物页），
> 裁剪比例是否仍适用需要实测确认。若 UI 改版把套装名往下挪，必须重新扫描这个值。

### 4.3 OCR

- 引擎：RapidOCR（`rapidocr_onnxruntime`），CPU 离线，原尺寸识别，**不要放大**（2x 置信度反降）。
- **不要按 y 重排行**：RapidOCR 输出顺序即阅读顺序。按 y 排会把「生命值 / 7.0%」
  颠倒成「7.0% / 生命值」，主属性解析随即失败。
- 性能分布（586×601、12 核）：det ≈ 180ms、cls ≈ 20ms、**rec ≈ 1000ms（85%）**。
  瓶颈在逐行文字识别。
- **预热必须用含真实文字的图**：用纯色/噪声图预热时 det 检测不到文字 → rec 根本没跑 →
  首次真实识别仍需 2.5s。改为启动时抓一张真实详情栏图预热后，首次即降到 1.2s 级。

### 4.4 字段提取：两个易混字段

| 位置 | 字段 | parser 是否使用 |
|---|---|---|
| 顶部大字 | **这一件圣遗物的名字**（如「止于荣礼的缎彩」） | ❌ 不使用 |
| 底部套装效果区标题 | **套装名** + 已装备件数（如「影中沉凝的幻灭：（0）」） | ✅ 匹配依据 |

裁剪下界切太狠会把套装名整行切掉 → 误判「套装不在库」。
也**不可**把「套装名：（N）」行当噪声过滤掉。

### 4.5 文本过滤

```python
NOISE = [圣遗物推荐, ^对\s*比$, ^强\s*化$, ^装\s*备$, ^重\s*塑$, 件套, [★☆]]
```

- **只要含 ★/☆ 就整行丢弃**：星级对本项目无用（只处理 5 星），
  且实测出现过 `6★` 这种「数字+星」形态，用 `^[★☆]+$` 会漏；
  漏下的 `6★` 经 parser 的 `replace(/★+/g,"")` 会留下孤立 `6`，有被误当数值的风险。
- **遇到套装名行即截断**：只过滤「件套」不够——4 件套描述常占 2~3 行，
  第二行形如「法器、弓箭角色时，角色重击造成的」会漏网。
- 行首项目符号（`·` `・` `：` 等）、行尾孤立引号（`指挥的礼帽”`）都要剥离。

### 4.6 套装名行的括号不可信

原文 `绝缘之旗印：（0）`，实测被读成过 `(0)`、`(O)`、**`(O0)`**（0 变字母 O，甚至一个 0 变两个字符）。

因此**判定只看「冒号 + 左括号」结构**，不校验括号内内容：

```python
SET_LINE_RE = re.compile(r"^[^：:]{1,20}[：:]\s*[（(]")
```

括号内容另用 `normalize_set_line()` 规范化（字母型数字修正 → 只留数字 → 取最后一位），
保证交给 parser 时是 `（0）`——它的未知套装启发式要求 `(\d+)`。

## 5. 可靠性：三道闸

### ① 完整性检查（服务端）

正常详情栏至少 8 行有效内容。实测有一次在画面过渡瞬间只识别到 2 行，
不是识别率问题而是抓到了切换动画中的一帧，必须判失败让用户重按，否则会给出残缺数据。

另：**带 `+` 却不含任何数字的行**（如 `防御力+`，数值整个丢失）一律标记可疑。

### ② parser 警告（前端）

`receiveOcrArtifact` 会检查 `parsed.warnings`。除「3 条激活副词条」属正常形态提示
（3 初始件就是这样）外，**任何警告都回退到录入弹窗**，并把第一条显示在 toast 里。

「未识别到套装/部位」「无法识别副词条片段」「副词条重复」这些情况下直接评估，
会算出**看起来正常但完全错误**的结论。

### ③ suspicious 提示（前端）

服务端的两类信号——多尺度不一致、残行——非空时 toast 提示「有 N 处数值可疑（原因），请核对」。

### ⚠ OCR 会在信息缺失时「编」一个数

实测：理之冠首条副词条被游戏光效**完全覆盖**（人工 4x 放大确认只有一片纯白、无字形残影），
OCR 仍输出 `攻击力+39`，**置信度 0.741**，与正常字段（0.839~0.863）同级，**用阈值筛不出来**。
经用户确认真值为 `33`。

同一位置 1x 读 `+39`、2x 读 `+3°` —— 多尺度比对能标出「可疑」，但两路都不等于真值。

**这不是识别错误，是幻觉。** 与「parser 不存主属性数值」叠加就是双重静默失败：
编数 → 正常接收 → 照常评分 → 用户无感。

> 副产品：这类编造值往往违反游戏档位规则。小攻击档位 `[14,16,18,19]`，
> k 次投档的合法和值仅 83 个——`33` 合法（14+19），`39` 不合法
> （35~45 之间只有 35/36/37/38/42/44）。可用于自动校验，
> 但需要精确档位（`ROLL_TIERS` 存的是四舍五入后的显示值，直接求和会误报）。

## 6. 配置

`service_config.json`（首次运行自动生成，**不入版本控制**）：

```json
{
  "process_name": "YuanShen.exe",
  "crop_ratio": [0.725, 0.055, 1.0, 0.52],
  "hotkey": { "modifiers": ["alt"], "key": "s" },
  "quit_hotkey": { "modifiers": ["alt"], "key": "q" },
  "skip_ocr": false,
  "save_frames": true,
  "keep_frames": 20,
  "multi_scale_check": false,
  "min_window_height": 900
}
```

- `save_frames` / `keep_frames`：每次识别存整窗图 + 裁剪图到 `debug/`，**只保留最近 N 组**。
  ⚠ 必须有这个限制：曾无清理堆到 144 张 / 205MB。现改为 JPEG(q85)，单张约 250KB。
- `multi_scale_check`：默认关闭。开启后两次 OCR，耗时从约 1.2s 涨到约 3.1s，
  且只能报警不能纠错，所以只在排查时开。

### 实测性能

常驻模式 5 次：**平均 1235ms**（1116 / 1136 / 1140 / 1314 / 1469）。
`--once` 模式每次约 4s（要重新加载模型 + 冷启动），**只用于调试**。

### 已知的测试环境限制

agent 进程运行在**非交互式会话**（`GetForegroundWindow()` 返回 0），
`keybd_event` 发出的按键进的是本会话输入队列，**到不了用户会话的热键**。
所以「按 Alt+S」这一环无法自动化，只能真人验证。

`fake_ocr_server.py` 就是为此而生：复用真实的 `OcrStore` / `OcrHandler`（协议一字不差），
只把数据来源换成固定样本。

## 8. 已知限制

| 限制 | 说明 |
|---|---|
| 窗口被遮挡即失效 | `BitBlt` 读屏幕合成结果，无焦点也行，但被盖住会抓到遮挡物 |
| OCR 随机波动 | 光效动画会让个别字时隐时现（实测 5 次里出现 1 次 `防御力+21` 读成 `防御力+`） |
| 耗时受 CPU 影响 | 游戏运行时 rec 阶段会被抢 CPU，实测 1.2~2.5s 波动 |
| 裁剪比例硬编码 | 窗口尺寸变化未验证；不做「首次运行自标定」（用户已确认） |
| 套装库需维护 | 新版本套装要同步 `js/constants.js` 的 `SETS`，否则只能按未知套装处理（会 toast 提示） |

## 9. 排障

**网页没反应** → 按 F12 看控制台：

```js
App.ocrBridge.status()   // base=null 没连上；running=true 且 lastSeq=0 连上但没收到件
fetch('http://127.0.0.1:18080/api/ocr/health').then(r=>r.json()).then(console.log).catch(console.error)
```

正常应看到 `[ocr-bridge] 已连接 http://127.0.0.1:18080`。

桥接**探测失败后每 10 秒重试**，所以服务比网页后启动也能连上，
`file://` 页面切到后台再回来会立即补一次轮询。

**识别内容不对** → 看 `debug/` 里最近一组 `*-panel.jpg`，确认裁到的是不是详情栏。
若裁到了别的界面，说明当时不在圣遗物页；若裁歪了，调整 `crop_ratio`。

**热键没反应** → 启动日志会明说注册失败（错误码 1409 表示被其他程序占用），
改 `service_config.json` 换键位。
