# 圣遗物评分网页 · 实现方案

> 基于已定稿的《圣遗物背景知识总结.md》与《圣遗物评分算法设计.md》实现。
> 目标：一个本地使用的圣遗物管理网页，覆盖数据管理、计算、评估与展示全流程。

---

## 一、项目概述

### 1.1 功能清单（用户需求）

| # | 功能 | 说明 |
|---|------|------|
| 1 | 角色圣遗物数据导入 / 导出 | 完整 JSON 导出备份、导入恢复（可选覆盖/合并） |
| 2 | 单件圣遗物词条计算 | 每件圣遗物的加权有效词条数（算法一） |
| 3 | 角色圣遗物评分 | 角色总分 + 完美态百分制 + 充能标签（算法二） |
| 4 | 圣遗物价值评估 | 新圣遗物相对已穿戴件是否有价值：情况一散件 / 情况一′ 自由件（无散件·冗余位，2026-09-28）/ 情况二套装替换 / 情况三套装件替换散件，含未满级强化潜力评估（算法三） |
| 5 | 数据与结果展示 | 角色列表、5 部位详情、评分卡片、评估结果，全部可视化 |
| 6 | 圣遗物重塑分析 | 判断哪些满级 5★ 圣遗物更值得消耗启圣之尘重塑：安全网期望 + 三情况归属（套装件→自己/同套宿主，散件→所属套装宿主）+ 三情况开关（原地强化/同套转移/晋升套装件任意组合过滤）+ RV 期望净提升排序 + 保底三档 + 3/4 初始自动推断（区间法：明确→静态展示，两可/无判据→切换按钮），覆盖角色已有件与新输入件（算法四，2026-09-12；归属规则 2026-09-27 v2；开关与初始推断 2026-09-28；推断判据改区间法 2026-10-10） |

### 1.2 设计原则

- **零部署**：双击 HTML 即用，数据存浏览器 localStorage
- **离线可用**：无后端、无外部 CDN 依赖（保证本地打开不联网也能用）
- **多角色**：支持多个角色独立管理
- **所见即所得**：录入即实时计算，修改即时报错

## 二、技术实现方案

### 2.1 技术选型

| 项 | 选择 | 理由 |
|----|------|------|
| 语言 | HTML5 + CSS3 + 原生 JavaScript（ES6） | 零构建、零依赖，双击即用 |
| 持久化 | localStorage | 本地存储，容量约 5MB，足够角色+圣遗物数据 |
| 结构 | 多文件模块（script 按序加载） | 无打包工具时用全局命名空间组织 |
| 图标/字体 | 内联 SVG + 系统字体 | 避免外部资源，保证离线 |
| 版本 | 无框架、无构建、无 npm | 最简部署 |

### 2.2 总体架构（分层）

```
┌─────────────────────────────────────────────┐
│  视图层 View        (渲染 DOM、事件绑定)       │
│  角色列表 / 角色详情 / 编辑弹窗 / 评估页 / 重塑分析 / 导入导出 │
│  反馈层 Feedback (feedback.js：模态框/toast/    │
│  confirm/prompt/info，全站交互反馈统一)         │
├─────────────────────────────────────────────┤
│  状态层 Store       (全局状态 + localStorage 同步) │
├─────────────────────────────────────────────┤
│  算法层 Core        (纯函数，无 DOM 依赖)       │
│  calcArtifactScore / calcPerfect /           │
│  calcCharacterScore / evaluateArtifact        │
├─────────────────────────────────────────────┤
│  数据层 Data        (数据结构、校验、导入导出、外部格式适配、文本识别) │
└─────────────────────────────────────────────┘
```

**核心原则**：算法层是**纯函数**（输入数据 → 输出结果），与定稿算法文档一一对应，便于测试与复用；视图层只负责渲染与交互。

#### 角色套装字段 `sets`（2026-10-09 新增，用户口径）

**语义**：固化「这个角色穿什么套装」，作为套装类判定（情况二/三、重塑宿主与自评）的**唯一来源**。

| 取值 | 含义 | 判定影响 |
|---|---|---|
| `[A]` | 四件套（4+1，含 5 件同套） | 正常产生套装类结论 |
| `[A, B]` | 两个两件套（2+2+1） | 同上（接受 2+2+1 参与评估） |
| `[]`（留空） | 其他（3+1+1、2+1+1+1 等） | **一切套装类判定停用**，只剩情况一/一′（纯词条 + 散件/自由位） |
| 未录全（5 部位任缺 `set`） | —— | **当这个角色不存在**：不读字段、不做一致性检测、不充当判定对象与宿主 |

- **为何新增**：此前「角色所穿套装」是遍历 `artifacts` 实时推导的（`wearsSet` 找非散件位同套件、`isSetPiece` 比较部位套装），但录入过程中数据增删会让这套推导飘忽、且无法表达「这个角色我就是按 2+2+1 玩」这类意图。改为**角色级字段固化**后，判定不再受录入完整度影响（未录全则直接弃权）。
- **读写链路（策略 b：字段权威、不在圣遗物变更时自动同步）**：
  - 读取：`core.roleSets(role)` → 门禁 `isFullyRecorded(role)` + 字段清洗（去空串、截断至 2）。派生 `core.hasSetInfo(role)`（总开关）、`core.isSetPiece(art, role)`、`core.wearsSet(role, setName)`。
  - 写入：角色配置弹窗的两个套装下拉（候选 = 自定义套装 + `constants.SETS` + 当前值）；保存时 `role.sets = [cSet1, cSet2].map(...).filter(Boolean).slice(0,2)`。
  - 一致性：`core.checkSetConsistency(role)` 比对**字段声明**与**从 5 部位实况推导的构成**（`core.deriveSetsFromArtifacts`），不符时在角色详情页显示黄色警示条 + 「按实况更新」按钮（仅告警与快捷修正，**不自动改写字段**）。仅在「5 部位录全 且 字段非空」时检测。
- **校验（`data.js.validateRoleConfig`）**：`sets` 必须是数组、元素为非空字符串、长度 ≤ 2 → 违反为硬错误；**字段缺失不报错**（向后兼容，交由迁移补齐）。
- **一次性迁移预填（`storage.prefillRoleSets`，跑在 `sanitizeStore` 内）**：仅当角色**完全没有** `sets` 键（`!Array.isArray(role.sets)`）时，用 `core.deriveSetsFromArtifacts` 从实况预填。
  - 键存在即视为「已迁移」——用户主动清空（`sets: []`）不会被再次填上。
  - **不 bump `STORAGE_VERSION`**（bump 会换 localStorage key、等于清空用户数据）；也不在 store 级写「已迁移」标记（会被导出/导入带出去，且导入旧备份时判断错乱）。以「字段是否存在」充当迁移标记。
  - 预填口径：4+1 / 5 件同套 → `[主套]`；2+2+1 → `[A,B]`；3+1+1 / 2+1+1+1 / 未录全 → `[]`（归「其他」）。
  - **实测（2026-10-09，本机 77 角色真实数据 · 浏览器端到端）**：预填后 1 个套装 = **73**、2 个套装 = 0、空 `[]` = 4、仍无字段 = 0（localStorage 与内存 store 一致）。4 个空值中：**申鹤 / 梦见月瑞希** 为 3+1+1 归「其他」；**五郎 / 莫娜** 为 5 部位未录全（当这个角色不存在）。预填后「字段 vs 实况」不一致 = **0**；二次 load **幂等**（localStorage 字节一致）；首页按角色筛选「翠绿之影」卡片数 = 字段命中数 = 4；详情页套装块 / 配置弹窗双下拉回显正常；无页面错误。
- **适配器不写该字段**（`adapters.js` 莫娜适配器）：与 `element` 同策略——**故意不写**，交由 `sanitizeStore` 在导入时统一补全/预填，避免两处逻辑分叉。
- **判定口径联动**（与字段新增同步调整）：`evaluateArtifact` 的情况二需要 `hasSetInfo`；`remodelTargets` 的「情况一（原地强化自评）」需要 `hasSetInfo(sourceRole)`；`wearsSet` 改读字段。因此**留空 / 未录全的角色不再产生任何套装类结论**（此前会有基于实况的推断结论）。
- **首页筛选**（见 3.2）：路径①「按角色」由「已录入件中该套 ≥2 件」改为 `core.roleSets(role).some(s => f.sets.includes(s))`——**直接读字段**，不再数件数。

### 2.5 数据持久化（storage.js）

```js
const STORAGE_KEY = "gys_reliquary_v1";

App.storage = {
  load()  { /* 读取 + 解析 + JSON.parse 容错；损坏时返回默认空结构并提示；迁移补过字段时回写 */ },
  save()  { /* JSON.stringify 写入 localStorage */ },
  migrate(raw) { /* 按 version 升级结构（预留）；customSets 必须透传 + 数据清洗 */ },
  sanitizeStore(store) { /* 数据清洗：删除废弃字段 note / mainValue + 补全角色 element + 一次性预填角色 sets（prefillRoleSets） */ }
};
```

- 每次数据变更（增删改角色/圣遗物）后 `save()`，**写失败（超容量）时弹提示并引导导出备份**。
- 读写统一入口，避免散落。
- **migrate 透传 customSets**（`Array.isArray(raw.customSets) ? raw.customSets : []`，emptyStore 同样含空数组）——2026-08-23 修复：此前 migrate 只保留 version/exportedAt/roles，导致自定义套装保存后刷新页面即丢失。
- **废弃字段剥离**（`sanitizeStore`，2026-09-28）：`migrate()`（加载路径）与 `io.importFile()`（导入路径）均先调用它，删除圣遗物上的 `note`（旧备注，曾由莫娜适配器写入「从莫娜占卜铺导入」）与 `mainValue`（主属性数值）——两字段已从数据模型中移除（见 2.4），历史备份/本地缓存经此自动清理，无需用户手动处理。
- **角色 element 自动补全**（`sanitizeStore`，2026-10-09）：`role.element` 缺失或为空串时按 `constants.CHARACTER_ELEMENT_HINTS[role.name]` 补值，**只填空值、绝不覆盖已有值**（用户手工选定的元素优先保留，映射表未收录的角色保持原样，不臆造元素）。同样跑在加载与导入两条路径上，故一处即可覆盖存量数据与后续导入，无需在莫娜适配器里另写一份。配套：映射表由 66 条补至 77 条（新增 叶洛亚/法尔伽/莉奈娅/尼可/布伦妮/洛恩/桑多涅/奥黛塔/薇斯纳/沃雅妮莎/兹白，值取自用户既有数据）。**动机**：此前 65 个角色该字段为空，界面虽能靠 `role.element || CHARACTER_ELEMENT_HINTS[role.name]` 兜底显示图标，但字段本身为空、导出数据不自洽。
- **加载时回写**（2026-10-09）：`load()` 在 `migrate()` 结果与 localStorage 原文串不一致时立即回写一次——否则「内存已补齐、存储仍为空」会出现「导出有 element、存储没有」的不一致，且每次打开都要重算。回写包在 `try/catch` 内，超容量/隐私模式静默忽略，不影响本次使用。
- **角色 `sets` 一次性预填**（`sanitizeStore` → `prefillRoleSets`，2026-10-09）：详见 2.4「角色套装字段」——仅补「完全没有该键」的角色，键存在即已迁移；不 bump `STORAGE_VERSION`、不写 store 级标记。加载/导入两条路径同时生效，且借上面的「加载时回写」自动落到 localStorage。
- **首页筛选状态独立持久化**（2026-08-23 起；**2026-09-28 升级为双路径结构**）：key = `gys_reliquary_filter_v{version}`（与角色数据分开）；结构 = `{ mode: "role" | "loose", slot, mainStat, sets }`——**落盘只保留当前路径的条件**（两条路径互斥）；`loadFilter()`（JSON 解析 + 形状校验：mode 白名单、slot/mainStat 字符串、sets 字符串数组；**兼容旧结构**（无 mode）——有件级条件（slot/mainStat）映射为 `loose`，否则映射为 `role`，且两路条件不混用；损坏数据返回 null 回退默认「全部」）/ `saveFilter(f)`（每次筛选变更、路径切换、清除时落盘，刷新/重新打开恢复上次筛选与所在路径）。

### 2.6 数据导入 / 导出（两种导入场景）

**导入分为两种场景，自动区分：**

```
选择文件 → 读取文本 → JSON.parse（去 BOM）→ 结构探测（detect）
              ├─ 本项目备份格式（含 version + roles）→ 全量校验 → 覆盖/合并
              └─ 外部格式（其他工具导出）→ 适配器转换（convert）→ 全量校验 → 覆盖/合并 → 提示统计与警告
```

> **实现说明**：转换结果不经过"可编辑确认面板"——直接校验后进入覆盖/合并；外部角色缺有效词条/权值等配置，由导入后提示引导进入「角色配置」手动补充（转换警告在导入成功的信息弹窗中列出）。

#### ① 备份导入（本项目格式）

- 结构：`{ version: 1, exportedAt, roles: [...] }`（可选 `customSets: [...]`）
- 流程：`JSON.parse` → version 兼容检查 → **全量深度校验**（逐角色、逐圣遗物，收集全部错误）→ 导入策略（覆盖 / 合并，重名确认）

#### ② 首次使用导入（外部格式适配器框架）

外部 JSON 由其他圣遗物工具导出，结构未知。**架构决策：适配器在网页内实现**（与"零部署、双击即用"原则一致；无需 Python 环境，避免割裂用户流程；适配器可长期复用——换设备/清缓存/新工具格式都会再次触发外部导入，并非一次性代码）。

适配器注册表将外部结构转换为本项目内部模型：

  },
  {

```

**已实现适配器：莫娜占卜铺（mona-chan）**（2026-08-17，依据 `mona.json` 样例开发）：

| 项 | 说明 |
|----|------|
| detect | version 为字符串 + 含 flower/feather/sand/cup/head 五数组 + 元素含 setName/mainTag/normalTags |
| 部位映射 | flower→flower, feather→plume, sand→sands, cup→goblet, head→circlet |
| 词条映射 | lifeStatic→生命值、attackStatic→攻击力、attackPercentage→攻击力百分比、critical→暴击率、cureEffect→治疗加成 等 19 种 |
| 套装映射 | 42 种英文 key → 中文名（含 6.x 新套装：影中沉凝的幻灭/天之美赐/风起之日/晨星与月的晓歌/纺月的夜歌/穹境示现之夜/深廊终曲） |
| 数值单位 | 百分比词条小数字段 ×100 转百分数（0.041→4.1）；数值词条原值 |
| 装备处理 | 仅导入 `equip` 非空（已装备）件并按角色分组；背包件（1991）不导入（本工具无背包结构），统计提示 |
| 角色配置 | effectiveStats/weights 留空（外部格式无此概念），erRequirement/currentER 默认 180，导入后需在角色配置中手动补充；**element 由 `sanitizeStore` 按角色名映射自动补全**（2026-10-09；映射表未收录的名字仍为空，可在角色配置中下拉选择） |
| 散件部位 | **依据套装分布智能推断**：件数为 1 的套装对应部位即为散件（1 件套无套装效果），装备 ≥4 件时按部位顺序取第一个单件套；覆盖 4+1（异套件）/2+2+1（单件套）/3+1+1；全同 5 件套或装备 <4 → null（无散件，可手动设置）——不再硬编码默认杯 |
| 数据来源 | 全部 4 条副词条已激活（莫娜无 3 初始），level 真实等级（可能非 4 倍数，remaining 公式已兼容） |

- **适配器职责**：`detect`（识别格式）+ `convert`（外部字段 → 内部模型 + 词条/套装/部位名称规范化）
- **新增适配器流程**：拿到外部 JSON 样例 → 分析字段结构 → 实现 detect/convert → 注册
- **角色配置需手动补充**：外部工具一般只含圣遗物数据（5 部位副词条），**不含本项目特有的"有效词条 / 词条权值 / 充能需求 / 面板充能 / 散件部位 / 角色套装"配置**——转换后默认留空（effectiveStats=[]，充能 180），导入成功提示用户进入「角色配置」补充后才能得到完整评分（其中 `sets` 会先按 5 部位实况自动预填，但**建议人工核对**，见 2.4）
- **`element` 与 `sets` 由适配器「故意不写」**（2026-10-09）：转换产物统一交给 `sanitizeStore` 补全（element 按角色名映射、sets 按 5 部位实况预填）——**一处逻辑覆盖加载与导入两条路径**，避免适配器里再抄一份、日后口径分叉。故莫娜适配器的角色对象里没有这两个字段。
- **导入校验放宽**：`validateStore` 只校验结构合法性（角色名唯一 + 圣遗物数据合法）；角色配置缺失不阻止导入（可后补），与「保存角色配置」时的硬校验（至少一个有效词条）相区分
- 转换后同样走**全量校验**，校验失败会定位到原始数据字段
- 导入成功后展示适配器统计：导入件数 / 背包未导入件数 / 转换警告（未知套装/词条/缺部位等）
- 无适配器匹配时：提示「暂不支持该文件格式，请提供样例以便适配」，并**展示原始 JSON 结构**供人工确认
- **演进边界**：若未来外部格式确实复杂（如 OCR 图片、海量批量清洗、需第三方 API），再评估拆分为独立程序；当前个人场景（单次/低频、零部署优先）维持网页内实现

**导出**（备份，完整 JSON）：
- 组装 `{version, exportedAt, roles, customSets?}` → Blob 下载 `圣遗物备份_YYYY-MM-DD.json`（带 BOM，UTF-8）；覆盖/合并导入时自定义套装随数据迁移（合并 = 并集去重）
- 导出前仅检查角色数非空（数据合法性由录入/编辑时的校验保证；保存失败（超容量）时 storage.save 提示尽快导出备份）

### 2.7 单件圣遗物录入（两种模式）

**模式一：文本识别（默认）** —— 粘贴一段文本自动解析：

```
输入示例：
空之杯雷元素伤害加成7.0%+0·攻击力+4.1%·生命值+4.7%·元素充能效率+6.5%·防御力+19（待激活）角斗士的终幕礼：(0)

识别结果：
部位 = 空之杯 → goblet
主属性 = 雷元素伤害加成（数值 7.0% 仅用于定位分段，不入库、算法不依赖）
等级 = 0（来源：主属性数值后的 +0；文本末尾「(0)」为冗余显示，忽略）
副词条 = 攻击力+4.1% / 生命值+4.7% / 元素充能效率+6.5% / 防御力+19（待激活）→ 3 条激活 + 1 条待激活（初始三）
套装 = 角斗士的终幕礼
```

**格式容错示例（2026-10-14 新增，均等价位识别）**：

```
① 副词条零分隔连写：
   时之沙攻击力7.0%★★★★+0·攻击力+14生命值+5.8%暴击伤害+7.0%·暴击率+3.9%天之美赐：（0）
② 冒号分隔（等级:副词条）：
   时之沙攻击力7.0%★★★★+0:攻击力+14 生命值+5.8% 暴击伤害+7.0%·暴击率+3.9%天之美赐：（0）
   两者识别结果一致：sands / 攻击力百分比 / 等级 0 / 4 条副词条（攻击力14、生命值%5.8、爆伤7.0、暴击率3.9）/ 天之美赐
```

**识别流程**（`App.parser.parseArtifactText(text)`）——**先合并成一行，再统一识别切割**（分行的位置不确定，不做行结构假设）：

**第 0 步：归一化** —— **删除所有 `★`（星级符号，与识别无关）** → 所有换行统一替换为 `·` 分隔符（任意分行位置都合并成一行）；分隔符集 = 任意空白（含单空格，兼容「生命值 717」名值同行）/ `·` / 顿号 / 逗号 / 分号；**冒号按分隔符处理**（如 `+0:攻击力+14` 等级与副词条之间），但「套装名:(N)」「套装名：（0）」的标注形态（冒号后紧跟数字/括号数字）保留不切，供未知套装启发式识别（见下方「未知套装识别」）。

**第 1~2 步：定位部位、套装** —— 部位/套装别名表最长匹配（空之杯→goblet、生之花→flower 等；角斗士的终幕礼 等套装名）。

**第 3 步：主属性 / 等级 / 副词条段划分**（片段分类，不依赖行结构）：
- 取「部位之后 → 套装之前」的内容，按分隔符切分为片段
- **等级依据 `+N` 判断（不依赖星级行 ★，`+` 后面跟着的一定是等级）**：
  - 独立等级片段（整体为 `+N` / `Lv.N`，如 `★★★★★+0` 归一化删 ★ 后为 `+0`、`Lv.12`）→ 从片段流提取并跳过
  - 紧凑格式主属性片段内数值**之后紧跟**的 `+N`（如 `雷元素伤害加成7.0%+0` → 0）；按匹配消费长度定位尾部，不把整段结尾的 `+N` 误当等级（如 `攻击力7.0%+0·攻击力+14` 中 `+14` 是副词条数值）
- **紧凑格式**：首个片段为「词条名+数值(+N)」→ 主属性 = 该片段（名/等级；数值仅用于定位分段，不入库），其余为副词条；数值（+等级）**之后**的残余文本（零分隔连写）并入副词条段继续解析，不丢弃
- **分段格式**：首片段为纯词条名（无数值）→ 前导片段依次为 主属性名 / 主属性数值（纯数值，可带 %，仅用于定位分段、不入库），其后为副词条
  - **主属性名歧义消解（结合数值单位）**：主属性名「攻击力/生命值/防御力」且数值带 % → 对应百分比词条（如「时之沙 攻击力 46.6%」→ **攻击力百分比**，不与副词条数值「攻击力」冲突）；数值不带 %（如「死之羽 攻击力 311」）→ 保持数值词条
- 两种格式自动识别切换，识别逻辑共用

**第 4~6 步：副词条拆分 / 初始判定 / 互斥检查**（共用逻辑）：

4. **副词条**：按分隔符拆分；片段内含**零分隔连写词条**时（如 `攻击力+14生命值+5.8%暴击伤害+7.0%`）按「词条名+数值」模式逐个切分（最长词条名匹配 + 消费长度推进），全程可无 `·`/空格等分隔符
   - `（待激活）` 标记绑定**其前一条**词条（标记出现在片段开头则绑定后一条），同片段其它词条不受影响
   - 词条名经**别名表**规范化：攻击力/小攻击→攻击力、攻击力%/大攻击→攻击力百分比、生命值/小生命→生命值、生命值%/大生命→生命值百分比、防御力→防御力、防御力%→防御力百分比、暴击→暴击率、爆伤→暴击伤害、精通→元素精通、充能→元素充能效率、雷伤→雷元素伤害加成 等
5. **初始判定**：副词条总数 = 4 → 初始四（全部激活）；= 3 激活 + 1 待激活 → 初始三；其余 → 提示补全
6. **互斥检查**：副词条之间、副词条与主词条不重复（不重复原则），重复则黄色警告

**词条消歧规则（识别精度关键）**：词条名匹配采用**最长前缀匹配 + 数值单位判定**——

| 词条文本 | 数值带 %？ | 识别结果 |
|---------|-----------|---------|
| 攻击力 +4.1% | 是 | 攻击力**百分比** |
| 攻击力 +19 | 否 | 攻击力（数值） |
| 生命值 +5.8% | 是 | 生命值**百分比** |
| 生命值 +299 | 否 | 生命值（数值） |
| 暴击 +7.4% | 是 | 暴击率 |
| 精通 +42 | 否 | 元素精通 |

- 先做最长词条名前缀匹配（避免"攻击力"误吞"攻击力百分比"），再按数值有无 `%` 判定数值/百分比词条
- 主属性同理：如「雷元素伤害加成7.0%」→ 雷元素伤害加成（词条名）

**识别容错**：
- 识别警告（未知套装/主属性/副词条片段、数量异常、互斥冲突等）以**黄色警告条**逐条列出在识别结果上方
- 识别结果预览表展示：部位/套装/等级/主属性/副词条（含待激活标记）；识别结果自动填入表单，可继续手动修正
- 一键切换到手动模式

**未知套装（自定义套装）识别**：
- **启发式识别**：未匹配到内置/自定义套装时，副词条段末尾的「套装名:(N)」「套装名：（N）」形态片段（半角/全角括号均可，如 `炉火融炼之心:(4)`、`炉火融炼之心：（0）`）识别为套装，**不再误报为副词条片段**；返回 `setUnknown=true`
  - 若套装标注与前一词条**零分隔连写**（如 `元素精通+23（待激活）炉火融炼之心:(4)`）：先把词条前缀切回副条流继续解析、套装名只取余下部分，避免前缀污染套装名
- **首次确认**：识别到新套装（`setUnknown=true`，不在 `C.SETS`/`store.customSets`）→ 弹窗确认「是否加入自定义套装？」；确认后写入 `store.customSets`（store 顶层数组，随导出/导入），并 toast 提示
- **再次识别直接命中**：`parseArtifactText(text, { customSets })` 将自定义套装并入套装候选——第二次识别同类文本直接命中，`setUnknown=false`、零警告
- **表单联动**：套装下拉 = 内置套装 + 自定义套装 + 当前表单值（已填自定义套装可回显），自定义输入框保留

**模式二：手动输入** —— 表单选择（部位/套装/主词条/等级/副词条行），即原方案的表单录入，与文本识别结果互通（可互相转换）。

### 2.7.1 新圣遗物「录入 → 评估 → 保存」流程（临时对象）

新圣遗物录入后**不直接保存**，作为**临时对象**流转：

```
录入（文本识别/手动）→ 临时对象 → 进入价值评估（算法三）
   ├─ 用户确认替换 → 写入角色 artifacts[slot]（旧件直接丢弃），重新计算评分
   └─ 用户放弃     → 丢弃，不落库
```

- 角色每部位只有 1 件，故新圣遗物必须**先评估、后写入**，避免覆盖现有件
- 录入入口：角色详情「＋ 录入新圣遗物」（单角色弹窗评估）与顶栏「价值评估」（全角色评估）——两者都走临时对象流程（部位卡已无"评估替换"按钮，评估统一收敛到这两个入口）
- 临时对象仅在评估会话内存在，不写入 localStorage；确认替换才触发角色更新与重算

### 2.8 校验与报错机制（关键）

用户明确要求"直接在网页中修改并报错"，校验分**硬性（阻止保存/导入）**与**软性（警示不阻止）**两级：

#### 圣遗物（Artifact）校验

| # | 规则 | 级别 | 报错文案示例 |
|---|------|------|-------------|
| 1 | 主词条与部位匹配（花=生命值、羽=攻击力） | 硬 | "花的主词条必须为生命值" |
| 2 | 副词条数量 3~4 条 | 硬 | "副词条数量必须为 3 或 4 条" |
| 3 | 副词条互不重复，且与主词条不重复（不重复原则） | 硬 | "副词条不能与主词条重复：暴击率" |
| 4 | 数值 > 0 | 硬 | "数值必须大于 0" |
| 5 | 数值 ≤ Umax × 6（单条词条最多 6 次 roll 的物理上限） | 硬 | "数值超出该词条的理论上限，请核对" |
| 6 | 百分比词条数值 ≤ 100（百分数口径，如暴击率应填 2.7~3.9 一类百分数） | 硬 | "暴击率为百分比词条，请填百分数（0~100）" |
| 7 | 待激活词条（activated=false）最多 1 条，且须有数值 | 硬 | "待激活词条数量不能超过 1 条" |
| 8 | level ≥ 4 时不允许有待激活词条（4 级已解锁） | 硬 | "4 级以上圣遗物不应存在待激活词条" |
| 9 | level 为 0~20 整数 | 硬 | "等级必须在 0~20 之间" |
| 10 | set（套装）必填 | 硬 | "请选择所属套装" |
| 11 | mainStat 必填 | 硬 | "请选择主词条" |

> 说明：副词条显示值是多次 roll 之和（初始 1 次 + 强化叠加），**可超过单发 Umax**（如暴击率显示值 7.4% > Umax 3.9%，对应算法文档 2.4 示例）。因此不做"≤ 单发 Umax"校验，仅做正值与物理上限（Umax × 6）校验。

#### 角色配置（RoleConfig）校验

| # | 规则 | 级别 | 报错文案示例 |
|---|------|------|-------------|
| 1 | effectiveStats 非空 | 硬 | "至少需要一个有效词条" |
| 2 | weights 覆盖全部 effectiveStats，且 0 < w ≤ 2 | 硬 | "有效词条必须配置权值" |
| 3 | looseSlot ∈ 5 部位 或为空（无散件） | 硬 | "散件部位不合法" |
| 4 | 5 个部位 artifacts 均已录入 | 软 | "还有 N 个部位未录入，评分暂不完整"（允许保存，评分区提示不完整） |
| 5 | erRequirement、currentER ≥ 100 | 软 | "充能需求/面板充能一般不低于 100%" |
| 6 | 角色名非空且唯一 | 硬 | "角色名不能为空 / 已存在同名角色" |
| 7 | 充能是有效词条但 erRequirement/currentER 未填 | 软 | "充能是有效词条，建议填写充能需求与当前面板充能"（不阻止保存） |
| 8 | element 非空时 ∈ 7 元素 | 软 | "元素「X」不在可选范围内" |
| 9 | sets 为数组、元素非空字符串、长度 ≤ 2（**字段缺失不报错**，向后兼容） | 硬 | "套装字段必须是数组 / 套装名必须是非空字符串 / 套装最多两个（四件套 1 个 / 两个两件套 2 个）"（见 2.4） |

#### 报错交互设计（实现现状）

- **录入弹窗**：点「保存」时 `validateArtifact` 汇总全部硬错误 → **信息弹窗（错误样式，红框 + 逐条列表）**列出，阻止保存（无逐字段红框）
- **角色配置弹窗**：点「保存」时 `validateRoleConfig` 汇总硬错误 → 信息弹窗列出；软性提示（未录全部位、充能 <100%）在角色详情评分卡/首页徽章以标签体现；重名等单条错误用 toast 提示
- **识别预览**：解析警告以黄色警告条列出（如互斥冲突、数量异常），保存时校验兜底
- **导入**：`validateStore` 列出每个角色的全部硬错误（角色名 + 字段路径），任一硬错误整体拒绝（信息弹窗展示）；角色配置缺失不阻止导入（可后补）；导入成功以信息弹窗展示统计与警告，关闭后刷新列表

### 2.9 算法层（core.js）

与定稿算法文档逐条对应，全部为纯函数：

  calcEnergyPenalty(role),             // 充能超额惩罚（直接全扣）
  calcCharacterScore(role),            // 角色总分 + perfectTotal + percent(封底0) + tags

  ERContrib(artifact),                 // 该件副词条充能贡献（面板口径 %）
  evaluateAgainst(newArtifact, oldArtifact, role),  // 核心比较（潜力+充能+判定+评分）
  freeSlots(role),                     // 自由位判定（2026-09-28）：可换异套件而不损失套装效果的部位；looseSlot 显式设置→仅该部位，为空→按「除该部位外 4 件同套」推断
  evaluateArtifact(newArtifact, role), // 主入口：情况一/一′/二/三 + 汇总

  deriveSetsFromArtifacts(role),       // 由 5 部位实况推导套装构成（仅供预填与一致性检测，不参与判定）
  sameSetComposition(a, b),            // 套装构成是否等值（顺序无关）
  checkSetConsistency(role),           // 字段声明 vs 实况 → {checked, mismatch, actual}

  // —— 算法四（重塑，2026-09-12；2026-09-27 三情况归属 v2）——
  expectedHits(n, k),                        // 安全网期望命中次数 E[Y_k]（X~B(n,1/2)，Y=max(X,k)）
  calcRemodel(artifact, role, k, initialCount),  // 单件重塑价值：E[remodel]/RV/达成度/保底三档/上限/尘耗/建议词条
  remodelSignature(art),                     // 圣遗物签名（跨角色去重键）
  inferInitialCount(artifact),               // 3/4 初始自动推断（2026-09-28 建 / 2026-10-10 改区间法）：显示值落在 k 发档位相容区间 → 总发数 9→4 / 8→3 / 两可或皆不可→null

```

实现要点：
- 数值口径：百分比词条 value 与 Umax 同为百分数（如 7.4 = 7.4%），避免当量失真
- `evaluateAgainst` 中的充能重算：`newER = currentER − ERContrib(old) + ERContrib(new)`，`ERContrib = Σ(副词条中充能显示值)`
- **充能不足不再否决替换（2026-09-29 口径变更 · 用户指示按方案 C）**：满级判定改为 **只看词条提升**（`worthy = diff > MIN_DIFF`），充能不足**仅提示不否决**——提示不参与判定；返回对象新增 `erConfigured` / `erOk` 字段供 UI 展示提示。提示文案与配色见下条「充能提示分级」。变更原因：原口径把「替换后 `newER ≥ erRequirement`」作为硬条件，而多数角色的 `currentER` 与 `erRequirement` 同值（导入占位默认 180/180，**零余量**），导致任何降低充能副词条、但词条当量明显更优的替换都被否掉（实测：七七换新羽 +1.21 词条仍被判「不建议替换（替换后充能不足）」）。已同步定稿《圣遗物评分算法设计.md》（§4.4 判定表 + 新增「口径变更记录（2026-09-29）」、§6/§9 小结、§4.5 示例 D）。
- **充能提示分级（2026-09-29 二次口径变更 · 用户指示）**：提示同时看「这次替换对充能做了什么」与「替换后是否达标」——`Δ = newER − currentER`（`role.currentER` 为替换前面板值），分四类：**Δ<0 且仍不足** →「充能不足，缺 X%」（`lack`，红）；**Δ>0 且仍不足** →「充能补足，还差 X%」（`partial`，黄）；**Δ>0 且达标** →「充能满足」（`met`，绿）；**Δ=0 或 下降但仍达标 或 充能未配置** → 无提示。`tags` 仍为文案数组（兼容），新增 `erTagLevel` 驱动配色，UI 侧由 `erTagCls(level)` 映射（独立评估页行 `.row-tag`、弹窗/详情页结果卡徽章共用）。变更原因：旧口径只看 `newER < erRequirement`，会把「正在补足充能的替换」（如 170% → 175%，需求 180%）也标成「充能不足」，与事实相反。⚠️ `erDelta` 取 2 位小数：`180 − 18.1 + 18.1 = 180.00000000000003`，不取整会把「充能未变化」判成「增加 → 充能满足」。
- **替换落库时联动面板充能（2026-09-29）**：`store.replaceArtifact` 在写入新件的同时，按**副词条充能贡献差**写回角色 `currentER`（`currentER ← currentER − ERContrib(旧件) + ERContrib(新件)`，与 `evaluateAgainst` 的 `newER` 同口径，保留 1 位小数），并返回 `{ ok, erFrom, erTo, erDelta }` 供 UI 提示。三条写入路径统一生效：独立评估页「替换」、评估弹窗「确认替换」、详情页「编辑已穿戴件」（后者在面板充能变化时 toast「面板充能已联动更新：180% → 172.9%」）。修复的问题：替换后面板仍显示替换前的值，首页充能徽章继续显示替换前状态（如已不达标却仍为绿色「达标」）。边界：仅当充能已配置（`currentER` 为数值）且差值非 0 时联动；主词条充能不在联动范围（评估路径要求主词条一致，替换不会改变主词条充能）。
- **充能「已配置」判定修正（2026-09-29）**：`erConfigured` 改用 `Number.isFinite()`——全局 `isFinite(null)` 会返回 `true`（`Number(null) === 0`），会把「未配置充能」（`null`）当成需求量 0%，从而对未配置充能的角色输出虚假的「充能不足」提示（同时 `erOk` 也会误判）。现要求 `erRequirement` 与 `currentER` **同时**为有限数值才视为已配置。
- **充能未配置时算法三跳过充能约束**（`erRequirement` 非数值）：不输出充能提示，替换后评分不扣充能惩罚——与算法二口径一致（充能非有效词条 → w=0 不惩罚）
- 判定与评分解耦、满级/未满级分支、封底 0 分，均照文档实现
- **情况一主词条匹配**：`evaluateArtifact` 的情况一/一′（作为散件 / 自由件）要求**主词条与被替换件一致**（主词条不同不算替换，不评估）——例如新火伤杯只对"现有杯主词条也是火伤"的角色评估；情况二（套装件）本就要求同套装+同主词条。这是对算法文档「主词条校验（可选）」的实现决策：当前以"与被替换件主词条一致"为必要条件（角色级"有效主词条"配置未引入）。
- **情况二排除散件**：`evaluateArtifact` 的情况二（作为套装件）要求该部位**不是散件部位**（`newArtifact.slot !== role.looseSlot`），即必须是套装件——避免同一件散件被同时以"情况一散件"和"情况二套装件"双重评估（角色散件部位的圣遗物不算套装件）。
- **套装类结论的总开关（2026-10-09）**：情况二/三、重塑的「情况一原地自评」与「宿主匹配」都属**套装类结论**，一律需要该角色**判套装**（`hasSetInfo` = 5 部位录全 且 `role.sets` 非空）：
  - `evaluateArtifact`：`isSetReplace` 增加 `setInfo &&` 前件（留空 / 未录全 → 不产生情况二）
  - `isSetPiece` / `wearsSet`：改读 `roleSets(role)`（此前分别比较"除散件位外任一部位 set"与"遍历非散件位找同套件"）
  - `remodelTargets`：`self` 行动增加 `hasSetInfo(sourceRole) &&` 前件（留空 / 未录全的持有者不再原地强化自评）；宿主匹配由 `wearsSet` 决定，同步收紧
  - **净效果**：留空（「其他」）或未录全的角色**只剩情况一/一′**（纯词条 + 散件/自由位判定，与字段无关），不再输出任何基于实况推断的套装结论
- **情况三（套装件替换散件）**：`evaluateArtifact` 的情况一中，若新件是**角色所穿套装的部件**（其 set 与角色除散件部位外任一部位 set 相同，`isSetPiece` 判断），则标记 `isSetSwap` 且 case = "散件(变为套装件)"——替换后该部位从散件变为套装件，角色将失去散件（looseSlot 置空）。替换确认时提示该变化；确认后 `role.looseSlot = null`。原神无 5 件套效果，故套装效果不变（若涉及凑齐 4 件套等效果增强，需套装效果数值模型，暂不纳入）。
- **情况一′ 自由件（2026-09-28 方案 A 修复）**：`looseSlot` 为空（无散件 / 全套装——**含 `null` / `undefined` / 空串 `""` 三种等价写法**，由 `hasLooseSlot` 统一判定，避免校验层认可的空串写法漏进「有散件位」分支）时，情况一不再整体跳过，而是按**自由位**（冗余位）评估——`freeSlots(role)` 判定「除该部位外其余 4 件均已录入且同属一套」，**5 件全同套 → 5 个部位全为自由位**（任意一件都是冗余件，换掉后仍是 4 件套，不损失套装效果）。修复前该情形只走情况二，**任何异套件都返回"无适用场景"**（把「自由度最大」误当成「无可评估自由度」）。
  - 守恒与去重：自由件与情况二共用同一被替换件与同一公式 → 新件为**同套同主词条**时优先记作情况二（标签更准确），情况一′ 跳过（`!isSetReplace` 守卫），避免同一件重复出结论
  - `isSetSwap` 收紧为 `hasLooseSlot(role) && isSetPiece(...)`（散件位为空串时同样不成立）：**looseSlot 为空时本无散件可失去**，不误判为情况三（否则 4+1 无散件角色把冗余位换成所穿套装件时会误弹"角色将失去散件"）
  - 保守边界：2+2+1 等分散套装、部位未录全 → `freeSlots` 为空 → 异套件仍不评估（换掉任一件都会破坏 2 件套）
  - UI：新 case 值 = `"自由件"`（`caseLabel` → 「自由件替换」，`caseRank` 归入情况一同组）；独立页图例第三项改为「散件 / 自由件替换」；"无适用场景"文案改为「该部位不是散件/自由位，且无同套装同主词条的已穿戴件」；角色配置「散件部位」label 补「5 件全套装可选『无散件』，此时按自由位自动评估」
- **充能联动边界**：`ERContrib` 仅计副词条充能。评估阶段由算法三算 `newER`；**确认替换/编辑已穿戴件后由 `store.replaceArtifact` 按同一差值自动写回 `currentER`**（2026-09-29 起，见上「替换落库时联动面板充能」）。主词条充能（充能沙 51.8% 等）不在联动范围：评估路径（情况一/二）本就要求主词条与被替换件一致，替换不会改变主词条充能；仅当将来放开主词条替换时才需补充主属性充能差
- **潜力叠加仅限已有副词条（对算法文档 4.2 公式的实现细化）**：强化只能叠加在**圣遗物已有副词条（含待激活）**上，不会凭空出现新词条。故潜力公式的叠加权重 = **该件圣遗物已有副词条中有效词条的最高权值**（`maxWExist`），而非部位级 `maxW(slot)`：
  - `potential = currentScore + pendingContrib + max(0, remaining − |pending|) × maxWExist`
  - 若已有副词条**全部为无效词条**（如防御力/生命值%/防御力%/攻击力 对主暴击爆伤角色），`maxWExist = 0` → 潜力 = currentScore（强化对评分无任何提升）
  - 效果：克洛琳德场景（新沙副词条全无效）潜力 = 0 ✓；示例 B（已有暴击率等有效词条）潜力 6.53 不变 ✓；示例 C（仅攻击力百分比 0.8 有效）潜力由 4×1.0=5.166 修正为 4×0.8=3.766（更贴合游戏实际，不假设能砸出不存在的暴击率）

- **算法四实现要点（重塑，2026-09-12；2026-09-27 三情况归属 v2）**：
  - 常量：`ROLL_AVG = 0.85`（70/80/90/100% 四档等概率期望）、`DUST_COST`（花/羽 1、沙/杯/头 2）、`REMODEL_K = {basic:2, advanced:3, oracle:4}`（constants.js）
  - `expectedHits(n, k) = n/2 + Σ_{x<k} C(n,x)/2ⁿ·(k−x)`——游戏「动态检测」（歪满保底缺口后剩余强化强制命中）与安全网 Y=max(X,k) 数学等价（NGA tid=47452649/45982193，已交叉验证其全部数值）
  - `calcRemodel` 返回 null 的情形：未满级（level<20）、无有效词条（w1≤0）——视图层据此过滤
  - 主排序用**基础档 k=2**（保守、不依赖账号圣言解明进度），UI 可切换 k=3/4 重排
  - **三情况归属（`remodelTargets`，取代 v1「跨角色取最优」）**：
    - 情况一：X 是持有者的套装件（`slot ≠ looseSlot` 且持有者 `hasSetInfo`）→ 评自己（baseline = X 对自己当前分，原地强化）
    - 情况二：套装件 + 宿主条件（Y ≠ 持有者、**Y 装备 X 所属套装**（`wearsSet` 读 `Y.sets`，2026-10-09 起；未录全/留空 → false）、Y 在同部位有同主属性件）→ 评宿主（baseline = 宿主现有件分，顶替转移）
    - 情况三：散件（slot == looseSlot）→ **不评自身**；仅评满足宿主条件的角色（X 对其是天然套装件，转移后凑更高件数套装）
    - 宿主现有件套装归属不限（是散件亦纳入）；新录入件视为无持有者游离件，按情况三口径评全部宿主
  - **统一 RV 骨架**：`RV = E[remodel] − 功能位现状分`（情况一减自己、二/三减宿主现有件）；`analyzeRemodel` 内覆盖 `currentScore = baseline` 并重算 `efficiency = RV/尘耗`，UI「现在 → 期望」直接沿用
  - **行动类别（kind）与三情况开关（2026-09-28）**：`remodelTargets` 给每个行动打 `kind` 标记——self（原地强化，情况一）/ transfer（同套转移，情况二宿主）/ promote（晋升套装件，情况三宿主；新录入游离件的宿主行动恒为 promote）；`analyzeRemodel` 第 5 参 `allowedKinds` 在行动循环处过滤（`Set.has(t.kind)`），**每件在开启范围内重新取 RV 最优**——单条行动的 RV 口径与全开时完全一致，开关只改变「取最优的范围」；全部关闭 → 空列表（UI 给出提示）。会话内状态 `remodelKinds`（不落盘，零数据模型改动）
  - **互斥取最优**：同一件的多个可评估行动互斥（重塑后的件只能在一处），每件取 RV 最大行动输出一条记录；无可评估对象（散件无宿主、行动全被关闭等）不进列表
  - **3/4 初始自动推断（`inferInitialCount`，2026-09-28）**：按「区间相容」判总发数（2026-10-10 口径变更，原为等值分解）——4 初始 = 4 发初始 + 5 次强化 = 9 发，3 初始 = 3 发初始 + 1 发解锁第 4 条 + 4 次强化 = 8 发；每条副词条显示值 v 只需落在「k 发档位和的相容区间」内：`k×(min档位 − half) ≤ v ≤ k×(max档位 + half)`，half = 面板显示舍入半宽（新增常量 `DISPLAY_HALF`：percent 0.05 / flat 0.5），k∈1..5（×100 整数化比较避免浮点尾差，每词条至多 5 次比较），四条可行 k 总和仅可 Σ=9 → 判 4、仅可 Σ=8 → 判 3；**两可或皆不可（异常录入 / 待激活条目不计判据）→ null 回退默认 4 初始**。**口径变更理由（2026-10-10）**：显示值本身是四舍五入后的结果，旧「等值分解」（k 发档位和必须**精确等于**显示值）把过强假设当硬条件，在档位和「跳档」处两头出错 —— 既漏判可行 k（实测 379 件中 130 件被误判「判不了」），又反向产生假唯一（70 件两可件被错判成确定值）；区间排除是必要条件（排除可靠）、包含只是「可能」，结论不失真。**已知取舍**：不再拦截「游戏不可能出现的显示值」（如暴击率 3.3），此类值按相容区间视为可行 k —— 仅影响手工录入笔误，真实数据不受影响。仅满级 4 条激活件有判据。UI **二态**：推断明确 → 静态标签 `.rm-init-static`（不可切换，防止把确定值误切）；推断 null → 切换按钮 `.rm-init`（会话内 `remodelInitOverride` 按签名记忆，仅对无判据件生效）。`initialCountOf` 链：**inferInitialCount（明确时忽略覆盖）> remodelInitOverride > 默认 4**
  - **零数据模型改动**：不新增持久化字段；3/4 初始（n=5/4）判定如上（推断 + 会话内手动覆盖 `remodelInitOverride`，按签名记忆），存量件无判据时默认 4 初始
  - 会话内新录入件走 `openArtifactModal(null, null, "remodel")`（mode 'remodel'）：保存时硬校验满级（未满级 info 弹窗阻止），入 `remodelTempList`（不落盘，可单件移除）；与存量件按签名合并去重（临时件优先）

### 3.2 页面 / 组件设计

**① 角色列表（首页 · 筛选 + 分数降序 + 单行信息总览卡片）**
- **排序**：按角色评分百分制**降序**排列（高分在前）
- **双路径筛选栏**（列表顶部；**两条路径互斥、切换即清空另一路**，2026-09-28 重构）：
  - **路径标签页**：「按角色」/「按散件」两个胶囊标签（`.filter-tabs .ftab[data-m="role|loose"]`，选中态品牌色描边 + 淡金底，高 30px 与下拉对齐）；点击切换路径 → **立即清空另一路条件**并落盘（两条路径不同时生效）

  - **副词条互斥（不重复原则）**：每个副词条下拉的候选 = 副属性全集 − 主词条（若属于副属性）− 其他行已选词条；任一副词条选中后，其他行的下拉自动排除该词条；主词条变化时同步刷新全部副词条候选

- **预填已有数据**：编辑已穿戴件 / 修改评估中的新圣遗物时，表单**自动回填**原数据（prefill 支持圣遗物对象或布尔；`true` 取角色该部位已穿戴件），并**默认进入手动模式**直接展示已填内容，便于修改；文本模式仍可切换重新粘贴

| 背景 | `--bg-0 ~ --bg-3` | 岩层深色系 `#131019 / #1c1826 / #262136 / #302a45`（页面底色 / 卡片 / 输入框 / 悬停） |

#### 组件规范

- **按钮体系**（`--t-fast` 过渡 + `:focus-visible` 金色描边）：
  - 主操作 `.btn-primary`：鎏金渐变 + 深色文字 + 投影，唯一视觉焦点
  - 次级 `.btn`：深灰渐变 + 描边，hover 亮金边框
  - 危险 `.btn-danger`：红色文字 + 红色描边 + 红色微光晕
  - 幽灵 `.btn-ghost`：透明背景，用于导航类弱操作（如「返回」）
  - 尺寸：`btn-sm / btn-md / btn-lg`；`btn-group` 用于详情页操作分组
- **徽章体系**（`.badge`）：胶囊形 + 1px 描边 + 半透明底（green/yellow/red/gray 四色）
- **模态框**：打开动画（scale 0.94→1 + fade，260ms ease）；头部 sticky + 渐隐底；关闭按钮 hover 变红；操作区 sticky 底部
- **Toast**：右上角堆叠，滑入淡出，左边框按类型着色，`aria-live="polite"`，自动消失不打断流程
- **空状态**（`.empty`）：圆形渐变图标底 + 标题 + 说明 + CTA 按钮（教育 + 引导双目标）

#### 明细规则

- **配色**：深色岩纹背景 + 鎏金强调（贴合原神 UI）；卡片无固定金色描边，颜色由部位达成度边框承载；部位徽章统一中性底，仅散件部位金色强调（不做按部位着色）
- **状态徽章优先级**（首页最右徽章，互斥）：缺部位（黄「缺位」）> 充能不足（红「充能」）> 充能达标（绿「充能」）> **未配置充能（灰「无充」）**；均以 title 悬停显示细节。未配置充能（有效词条不含「元素充能效率」）时以中性灰色「无充」占位（不误导读数，且与「充能/缺位」同为 2 字，跨角色列对齐）
- **情况优先级颜色（评估结果）**：金色（case-3 套装件替换散件）> 紫色（case-2 套装件替换）> 灰蓝（case-1 散件 / 自由件替换），以左侧色条 + 同色边框区分，颜色体现优先级
- **数值高亮**：有效词条数值绿色加粗，无效词条灰色；待激活词条半透明 + 「待激活」徽章
- **当量小字**：每条副词条右侧显示「×0.897」（当量，两位小数）；副属性/数值/当量三列 grid 固定列宽对齐
- **充能标签**：首页状态徽章 = 达标绿「充能」/ 不足红「充能」（title 显示「充能不足，缺 X%」）/ 缺部位黄「缺位」（title 显示未录数量）/ 未配置充能灰「无充」（title 显示「未配置充能（有效词条不含元素充能效率），评分不涉及充能」）；详情页评分卡不显示徽章，充能不足改为信息块内黄色小字「缺 X%」（仅配置充能的角色显示充能块）
- **部位达成度边框分级**（详情页部位卡，整卡边框 = 达成度）：达成度 = 单件词条数 ÷ 该部位完美词条数 `calcPerfect(slot)` × 100（完美为 0 时按 0%）；>80% 红 / 70~80% 橙 / 60~70% 紫 / 50~60% 蓝 / <50% 绿——2px 四边统一边框 + 百分比文字同色 + 微光晕，卡片背景不染色（避免杂乱）
- **视图切换动画**：`render()` 时主区域 260ms 淡入 + 6px 上移
- **滚动条**：金色细条 thumb（WebKit + `scrollbar-color` 双写）
- **减弱动效**：`@media (prefers-reduced-motion: reduce)` 下动画/过渡时长归零（无障碍）
- **favicon**：内联 SVG 金色角标（data URI，无外部资源）；`<meta theme-color>` 匹配页面底色
- **响应式断点**（三段）：
  - `≤900px`：角色卡片有效词条区/部位徽章区取消固定宽度（改自适应换行）

## 六、边界与限制

1. **localStorage 容量**约 5MB：当前数据结构（角色×圣遗物）远用不满；写失败时提示导出备份。
2. **仅本机使用**：数据存当前浏览器；换设备/清缓存需手动导出导入。
3. **无后端**：不支持多端实时同步；如需可后续加"导出分享链接"或部署静态托管。
4. **浏览器兼容**：现代浏览器（Chrome/Edge/Firefox/Safari 近两年版本）。
5. **校验口径**：数值上限按定稿 Umax；游戏内实际数值为档位组合，网页只做范围校验，不做离散档位强校验（软性提示偏高项）。
6. **算法边界**：完美态基准按 4 初始；3 初始圣遗物评分天然略低（符合游戏实际，见算法文档第 10 条）。
7. **外部导入**：莫娜占卜铺适配器已实现（2026-08-17，基于 mona.json 样例，42 套装/19 词条/5 部位映射，125 项回归测试覆盖）；其他工具格式仍待样例后扩展，无适配器时提示并展示原始结构；外部格式一般不含角色配置（有效词条/权值/充能），需导入后手动补充。
8. **文本识别容错**：识别基于别名表与正则，异常文本（未知套装/简称/格式变体）会黄标提示并允许手动修正，不保证 100% 识别；**先删除所有 ★、归一化换行合并成一行再识别切割**（分行位置不确定，不做行结构假设），**等级一律依据 `+N` 判断**（独立 `+N`/`Lv.N` 片段，或主属性数值后 `+N` 尾巴）；**主属性名歧义消解**——「攻击力/生命值/防御力」名 + 数值带 % → 对应百分比词条（不与其数值词条冲突），数值不带 % → 数值词条（如羽攻击力 311）；主属性数值仅用于定位分段，不入库、不展示、不参与算法；文本中其他 `(N)`（如套装名后）为冗余显示，忽略。
9. **词条消歧**：词条名最长前缀匹配 + 数值单位（`%` 有无）判定，区分数值/百分比词条（如 `攻击力+4.1%` → 攻击力百分比，`攻击力+19` → 攻击力）。
10. **新圣遗物为临时对象**：录入后不直接保存，先进入价值评估；确认替换才写入角色（旧件丢弃），放弃则不入库（见 2.7.1）。
11. **充能联动边界**：面板充能联动仅按副词条充能差计算，评估与落库同口径——确认替换/编辑已穿戴件后 `store.replaceArtifact` 自动把差值写回 `currentER`（2026-09-29）；主词条充能（充能沙→攻击沙等）不在联动范围，评估路径本就要求主词条一致故不会发生。
12. **0 级档位选择**：等级 = 0 时副词条数值控件为档位下拉（5★ 单次 roll 四档显示值，存于 constants.ROLL_TIERS，第 4 档 = Umax，如防御力百分比 5.1/5.8/6.6/7.3）；等级 > 0 恢复数字输入（强化后为多次 roll 之和，无固定档位）。档位为游戏内四舍五入显示值，与算法数值口径一致。
13. **仅满级可替换**：价值评估（独立页与角色详情弹窗）的替换按钮（「替换」/「确认替换」）**仅在新圣遗物满级（level=20）时显示**；未满级只输出强化判定（值得强化/不值得强化，判定基于"潜力 ≥ 现有散件"），**不提供替换入口、也无提示文案**——与算法三「未满级不做替换判定」的设计一致。
14. **潜力仅叠加已有副词条**：强化只能叠加在圣遗物**已有副词条（含待激活）**上（游戏机制），叠加权重取"已有副词条中有效词条的最高权值"，全部无效则潜力 = 当前词条数（如克洛琳德场景全无效副词条 → 潜力 0）；不假设能砸出圣遗物中不存在的词条（见 2.9 实现要点）。
15. **重塑分析为期望口径且零数据模型改动（2026-09-12）**：RV = E[remodel] − 功能位现状分为**期望净提升**而非保证（重塑结果可预览、可放弃）；初始词条按 ROLL_AVG=0.85 当量近似（无偏，每条 ±0.15 波动）；3/4 初始不持久化——推断明确者静态展示、无判据者默认 4 初始且仍可在卡片「初始」按钮会话内切换（存量数据无法区分 3/4 初始，游戏重塑界面可直接查看）；充能词条按权值线性参与，达标/缺充能的阶跃价值未刻画（需结合算法二充能标签人工复核）；新录入件为会话内临时对象（不落盘，与 2.7.1 评估临时对象同策略）。
16. **重塑候选跨角色去重**：同一件物理圣遗物可能出现在多个角色身上（重复录入），按签名（set+slot+mainStat+level+副词条序列）去重，保留首个归属角色展示「来自 X」——去重只影响列表展示，不影响计算口径（该件的可评估对象仍按三情况规则对全部角色判定）。
17. **重塑归属边界（三情况，2026-09-27）**：评估对象由归属规则确定——套装件评自己与同套宿主，散件仅评所属套装的宿主（不评自身）；散件无宿主、持有者外无可有效配置的件不进列表（汇总条注明）；情况二 RV 略高估（未计入持有者套装被打破的代价）、情况三 RV 略低估（未计入宿主凑件数后的再优化收益），偏差方向固定并在卡片文案提示；「Y 装备 X 所属套装」按"Y 非散件部位存在 set == X.set 的已穿戴件"判定，宿主现有件的套装归属不限。
18. **无散件（looseSlot 为空）的自由位口径（2026-09-28）**：`looseSlot` 为空时算法三按「冗余位」自动识别**自由位**——该部位可换成异套件而不损失套装效果（判据：除该部位外其余 4 件均已录入且同属一套）。5 件全同套 → 5 个部位**全部**为自由位（原神无 5 件套效果，任意一件都是冗余件）；4 件同套 + 1 件异套 → 仅那 1 件；2+2+1 等分散套装或部位未录全 → 无自由位，异套件仍返回「无适用场景」（保守——换掉任一件都会破坏 2 件套）。显式配置 looseSlot 的行为完全不变；`isSetSwap`（情况三）仅在显式配置了散件位时成立（无散件可失去）。「未设置」的三种写法（`null` / `undefined` / 空串）必须同口径——空串是校验层认可的合法「无散件」值，历史持久化 / 导入数据可能带空串（`hasLooseSlot` 统一判定）。
19. **藏品库（2026-10-11）**：见下节「七、藏品库」——**迁移红线**：`collection` 必须随 `emptyStore` / `migrate` / `sanitizeStore` / `replaceStore` 透传（与 `customSets` 同级）。

## 七、藏品库（未装备圣遗物的极限单件收藏，2026-10-11）

> 需求来源：2026-10-11 用户口述 + 藏品清单。**藏品** = 未装备给任何角色的圣遗物。
> ⚠️ 术语区分：**藏品 ≠ 散件**（散件 = 角色身上不参与套装的那个位置 `looseSlot`）；也**不要叫「单件」**（该词已被算法一占用，泛指任意一件）。

### 7.1 概念与数据

| 术语 | 含义 |
| --- | --- |
| **藏品件** | 未装备给任何角色的圣遗物，存于 `store.collection`（与 `roles` 平级，随导出 / 导入走） |
| **桶** | 「部位 + 主词条」，共 **26 个**（见 7.2） |
| **维度** | 6 个收藏维度：**双爆 / 攻击% / 生命% / 防御% / 精通 / 充能**（`双爆 = 2×暴击率 + 暴击伤害`）。**数组顺序即界面渲染顺序，双爆列首**（2026-10-11 用户要求） |
| **位** | 桶 × 维度，共 **95 个位**。**一件藏品可同时占据多个位**；被新件完全取代（不再占任何位）的件**自动删除** |

### 7.3 关键公式

```
维度值 dimValue(art, dim)
  单条维：该词条副词条值；双爆维：2 × 暴击率 + 暴击伤害      （计入 activated=false 的待激活词条）

理论满值 FULL[dim, 桶] = (该维度在该桶的「可用副词条槽数」 + 5) × 单发满挡贡献   （4 初始口径）
  可用槽数 = 维度涉及词条中「不与主词条冲突」的条数
  单条维：6 发 → 攻击% 34.8 / 生命% 34.8 / 防御% 43.8 / 精通 138 / 充能 39
  双爆维：一般桶 7 发 → 54.6 ；暴击头 / 暴伤头（主词条占掉一支）6 发 → 46.8

极限程度 = dimValue ÷ FULL                    // 0~1
潜力（乐观上限） = 当前值 + (该件已有该维度词条 ? rem × 单发满挡 : 0)
                rem = max(0, 5 − floor(level/4) − 待激活词条数)      // 可叠加次数（3 初始解锁占 1 次）

止损容错（2026-10-13 用户要求，「满级可期」件的强化止损线）：
need      = 最小的 k 使「当前值 + k × 单发满挡」严格超过藏品值 cur   // 全命中且满值口径
tolerance = rem − need        // 还能容忍几次「没加到该维度」——歪满 (tolerance+1) 次后即无望
```

- 「可用槽数」是**充能沙自动少一维、暴击头双爆维降为单支**的唯一依据（`constants.collectionUsableSlots`），无需硬编码排除项。
- 全 26 桶中**只有暴击头 / 暴伤头**的双爆维是 1 槽（46.8），其余皆 2 槽（54.6）。
- 止损容错：仅「未超过但满级可超」（`worse && canExceed`）的维度计算（`need/tolerance`，否则 null）；浮点比较与 `canExceed` 同为 ×100 整数化；容错是**状态函数**——从当前数值直接算，无需记录历史歪次数（已歪损失已含在当前值中）。

### 7.4 四大分析（新件 X vs 藏品库）

| 功能 | 规则 |
| --- | --- |
| **(a) 入藏判定** | 逐维度比对：`cur == null` → 可入藏（新维度）；`v > cur` → 可入藏（刷新纪录 +Δ）；否则未超过（Δ ≤ 0） |
| **(b) 择优替换** | 入库后按「位 → 持有者」重算：旧件**不再占据任何位** → 删除；**还占着别的位** → 保留 |
| **(c) 极限程度** | `dimValue ÷ FULL`（百分比 + 进度条） |
| **(d) 潜力** | 乐观上限；**强化不新增词条种类**，故没有该词条的件潜力 = 当前值 |
| **(e) 止损容错（2026-10-13）** | 对「未超过但满级可超」的维度：`need` = 最少还需命中几次（全命中且满值口径）、`tolerance = rem − need` = 还能歪几次——用于「满级可期」件的强化止损（歪满 tolerance+1 次即无望） |

> 「位 → 持有者」与「冗余件」由 `core.collectionIndex` 动态算出；浮点比较统一 ×100 整数化（并列最大值均视为持有者）。

### 7.5 藏品件参与算法四（重塑）

藏品件是**游离件**（`sourceRole = null`），只能走**情况三（promote）**：

```
可评估对象 = remodelTargets(X, null, roles)
           = 「穿着 X 所属套装 且 在同部位已穿同主词条的件」的角色（宿主）
权值       = 宿主角色的 weights / effectiveStats      ← 与角色件同一把尺子
RV         = E[remodel] − 宿主该功能位现有件分
```

- **不引入「通用权值」之类替代口径**（曾拟此方案，2026-10-11 用户指出其违背算法四「权值按角色取」的原意后废弃）。
- **无宿主则不产生评估行**。2026-10-11 实测用户 93 件藏品：21 件有宿主 → 19 件可算出 RV（2 件因宿主有效词条与藏品词条完全不沾而跳过）→ 仅 2 件 RV > 0。这是算法四的必然结果，不是漏算。

### 7.8 边界与风险

1. **迁移红线**：`collection` 与 `customSets` 同类——`emptyStore` / `migrate` / `sanitizeStore` / `replaceStore` **以及 `io.exportBackup` / `io.mergeStore`** 漏传即「导出有、刷新后没有」，或**导出备份不含藏品、导入后藏品被清空**（后者 2026-10-11 实际发生过，已修并补测试）。
2. **件可占多位**：不设「退役」标记，是否在藏由 `collectionIndex` **动态算出**；只有「无任何位选中它」的件才删。
3. **入库保护**：`store.pruneCollection(keep)` 排除本次操作件——用户主动收藏的件即使暂时不占位也不会被系统丢掉。
4. **同一件既在角色身上又在藏品库**：不强制去重；重塑候选按 `remodelSignature` 去重（现有机制）自动合并。
5. **藏品件不参与算法二 / 算法三的角色视角**：没有角色 → 无有效词条与权值；藏品比对走独立的「藏品视角」口径，这是设计使然。
6. **理论满值含「5 次强化全中同一维度」假设**，是数学上限而非现实可达值 → 极限程度普遍偏低属正常。
7. **3 初始件**上限略低（单条 5 发 / 双爆 6 发）；分母统一按 4 初始口径归一，潜力按**可叠加次数**（`rem − 待激活词条数`，2026-10-13 修）计。
8. **只收藏 26 个桶**：不在桶内的件 `analyzeCollection` 返回 `inScope: false`，UI 提示「不参与藏品比对」。
9. **暴击头 / 暴伤头的双爆维是「单支」**：满值 46.8（一般桶 54.6），天然偏低——正常现象。
10. **藏品件的重塑是「替代」口径**：无宿主不进列表（见 7.5 实测）。

- **开关实现**：`js/appearance.js`（点击切换 + 写 localStorage + 同步 ☾/☀ 图标与 `aria-label`）；`style.css` 末节 `.appearance-toggle`（34×34 图标按钮）；`index.html` 三处 —— `<head>` 内联引导脚本（首屏渲染前套用已存选择、消除闪烁）、顶栏 `#appearanceToggle` 按钮、`</body>` 前的脚本引入。**三处可整体删除**，其余代码零依赖。

**⚠️ 踩坑（已修）**：批量替换使用处时把 `:root` 里的 **token 定义行本身**也命中了，产生 `--fill-1: var(--fill-1)` 这类**循环引用**（13 处），导致深色模式下按钮 / 胶囊 / 毛玻璃**全部透明**；而浅色模式因为定义为黑色叠加而幸免，**掩盖了问题**（只测浅色会漏掉）。
**修法**：批量替换必须排除定义行（`.workbuddy/fix_selfref.py` 逐行断言自引用）。此后新增 token 一律**先替换使用处、后写定义**。
